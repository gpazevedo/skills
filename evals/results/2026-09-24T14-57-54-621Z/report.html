## Not ready — it's missing the details that drive implementation

The three stories describe *intent* but not *behavior*. Before I'd write code, I'd need answers to:

**1. Coupon shape & discount logic**
- Percentage off, fixed amount off, or both? Any cap on percentage discounts?
- Applied to cart subtotal, per-line-item, or post-tax/post-shipping total?
- Can it drop the total below zero? Below some minimum (e.g., $0 or shipping cost still due)?
- One coupon per order, or stackable? If stackable, in what order and does one override another?

**2. Validation rules beyond "expired"**
The story only calls out expiry, but "reject with a reason" implies a general validation framework:
- Non-existent/misspelled code
- Already redeemed (single-use vs multi-use vs per-customer-limit)
- Not-yet-active (start date in the future) — is that also "expired," or a separate reason?
- Minimum cart value / eligible items/categories not met
- What are the exact reason codes/messages returned to the shopper? (matters for both UI and tests)

**3. Case insensitivity mechanics**
- Is matching case-insensitive-only, or also whitespace-trimming (`" SAVE10 "`)?
- Are codes normalized at creation time (stored uppercase) or normalized at lookup time? This affects uniqueness constraints — is `SAVE10` and `save10` the same coupon or a collision to reject at creation?

**4. Unstated but necessary for "checkout"**
- Is this validate-only (return discount amount) or does it also *consume* the coupon (decrement uses, mark redeemed)? That's a very different transactional design.
- What happens if the same coupon is applied, checkout abandoned, and retried — is a "hold" released?
- Concurrency: two shoppers racing on the last use of a limited coupon.

## What I'd test once these are resolved

- **Apply valid coupon** → correct discount computed and reflected in order total.
- **Case insensitivity** → `save10`, `SAVE10`, `SaVe10` all resolve to the same coupon.
- **Expired coupon** → rejected, with the specific "expired" reason surfaced (not a generic error).
- **Not-yet-active coupon** → rejected with a distinct reason from "expired" (if that's a separate state).
- **Unknown code** → rejected with an appropriate reason, no crash on `undefined`/lookup miss.
- **Boundary on expiry** → coupon valid at `expires_at - 1s`, invalid at `expires_at` (need to know if expiry is inclusive/exclusive).
- **Discount doesn't produce a negative or invalid total** (if that's a rule).
- **Reuse/redemption limits** if in scope — single-use coupon rejected on second attempt.
- **Idempotency/concurrency** if coupon consumption is part of this slice — two simultaneous applies of a last-use coupon shouldn't both succeed.
- **Whitespace handling** on input code, if that's part of "case insensitive... easier typing."

I'd push back to the spec author on points 1–3 above before starting — particularly discount type/shape and the full set of rejection reasons, since those define the core data model and API contract, not just edge cases.
